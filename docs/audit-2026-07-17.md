# Аудит коду Miniflux Reader

Дата: 17 липня 2026 року

Режим: лише аудит, без змін у коді застосунку

## Резюме

Код загалом добре структурований і містить низку продуманих локальних оптимізацій. Водночас поточну версію не слід вважати безпечною для публічного розгортання, доки не усунуто SSRF та ризики виконання неперевіреного HTML.

Рекомендований порядок робіт:

1. Закрити SSRF та публічні server-side fetch endpoint-и.
2. Додати санітизацію перед усіма `{@html}`.
3. Впровадити streaming limits, timeout, rate limiting та обмеження конкурентності.
4. Додати `svelte-check`, lint і тести до обов'язкових перевірок.
5. Виправити scroll tracking, повторний DOM parsing і синхронні записи кешу.
6. Декомпозувати великі store та component файли.

## Критичні знахідки

### P0 — публічний SSRF / внутрішній HTTP-проксі

Кілька маршрутів дозволяють серверу виконувати запити до довільного `http(s)` URL:

- [`fetch-page/+server.ts`](../src/routes/api/fetch-page/+server.ts#L23)
- [`og-image/+server.ts`](../src/routes/api/og-image/+server.ts#L17)
- [`rss-bridge/+server.ts`](../src/routes/api/rss-bridge/+server.ts#L89)
- [`proxy/[...path]/+server.ts`](../src/routes/api/proxy/%5B...path%5D/+server.ts#L10)
- [`settings/+server.ts`](../src/routes/api/settings/+server.ts#L28)

Перевіряється переважно лише протокол, тому потенційно доступні loopback, LAN, Docker network, link-local та cloud metadata адреси. Redirect також може перевести дозволений URL на приватну адресу. Частина endpoint-ів узагалі не потребує автентифікації.

Рекомендації:

- Винести всі зовнішні запити в єдиний `safeFetch`.
- Заборонити loopback, private, link-local, ULA та multicast IPv4/IPv6 після DNS resolution.
- Перевіряти кожен redirect вручну.
- Для Miniflux зробити `ALLOWED_MINIFLUX_SERVER` обов'язковим у production і застосовувати його також у proxy.
- Захистити допоміжні endpoint-и сесією та rate limiting.

### P1 — XSS через неперевірений HTML

HTML вставляється без локальної санітизації:

- [`EntryContent.svelte`](../src/lib/components/content/EntryContent.svelte#L57)
- [`AiRuleAssistant.svelte`, before](../src/lib/components/content/AiRuleAssistant.svelte#L292)
- [`AiRuleAssistant.svelte`, after](../src/lib/components/content/AiRuleAssistant.svelte#L302)

`processArticleHtml()` змінює DOM, але не видаляє `onerror`, небезпечні URL, `object`, `embed`, форми чи небезпечні iframe. Основний контент покладається на санітизацію Miniflux, а AI-preview додатково обробляє недовірений результат моделі. Prompt injection може змусити модель згенерувати HTML у `replace()`.

Наслідки особливо серйозні, бо Miniflux та AI токени зберігаються в `localStorage`: [`auth.svelte.ts`](../src/lib/stores/auth.svelte.ts#L8).

Рекомендації:

- Санітизувати HTML безпосередньо перед кожним `{@html}`.
- Використати суворий allowlist, видаляти `on*` атрибути та небезпечні URL-схеми.
- Дозволяти iframe лише для визначених хостів і додавати `sandbox`.
- Додати CSP та Trusted Types.

### P1 — DoS через необмежене буферизування

Заявлені обмеження розміру застосовуються після повного `response.text()` або `arrayBuffer()`:

- [`fetch-page/+server.ts`](../src/routes/api/fetch-page/+server.ts#L49)
- [`og-image/+server.ts`](../src/routes/api/og-image/+server.ts#L37)
- [`rss-bridge/+server.ts`](../src/routes/api/rss-bridge/+server.ts#L51)
- [`proxy/[...path]/+server.ts`](../src/routes/api/proxy/%5B...path%5D/+server.ts#L53)

Hostile endpoint може нескінченно передавати дані або тримати connection відкритим. Більшості запитів також бракує timeout.

Рекомендації:

- Читати `ReadableStream` порціями та переривати запит після досягнення ліміту.
- Додати timeout до всіх upstream fetch.
- Додати глобальні concurrency limits і rate limiting.

## Інші проблеми безпеки

### P2 — кешування приватних відповідей

Authenticated API-відповіді не мають `Cache-Control: no-store`. `/api/settings` і `/api/proxy` використовують однакові URL для різних користувачів і не задають `Vary`, що створює ризик за наявності CDN або proxy-кешування.

Рекомендація: встановити `Cache-Control: no-store` щонайменше для `/api/settings`, `/api/proxy` та `/api/ai`.

### P2 — відсутність security headers

У репозиторії не налаштовано CSP, `frame-ancestors`, `X-Content-Type-Options` та `Permissions-Policy`.

Рекомендація: централізовано додавати їх у `hooks.server.ts` або на reverse proxy, залишивши конфігурацію в репозиторії задокументованою та перевірюваною.

### P2 — сирі токени в auth cache

`authCache` утримує сирі токени в ключах `Map`: [`settings/+server.ts`](../src/routes/api/settings/+server.ts#L17).

Рекомендація: використовувати HMAC або хешований ключ і регулярно видаляти прострочені записи.

### P2 — Docker hardening

Runtime-контейнер працює під root і містить усі dev-залежності: [`Dockerfile`](../Dockerfile#L9).

Рекомендації:

- Запускати процес під `USER node`.
- Копіювати лише production dependencies.
- Закріпити базовий image digest для відтворюваних збірок.

### P3 — dependency advisory

`pnpm audit` знайшов одну low-вразливість у `cookie@0.6.0`, транзитивно через SvelteKit. Застосунок наразі не використовує cookies, тому практична експлуатація малоймовірна, але lockfile слід оновити після появи сумісного patched dependency tree.

## Продуктивність

### P1 — повторний DOM parsing

Кожна зі 100 статей парситься через `DOMParser` щонайменше двічі для thumbnail і description, а CSS-selector feeds — тричі: [`entries.svelte.ts`](../src/lib/stores/entries.svelte.ts#L163).

Рекомендація: об'єднати thumbnail, description і publication date extraction в один parse/enrichment pass.

### P1 — окремий observer для кожного рядка

Кожен рядок створює власний `IntersectionObserver`: [`EntryRow.svelte`](../src/lib/components/content/EntryRow.svelte#L107).

Рекомендація: використовувати один observer на список із реєстрацією та видаленням елементів.

### P1 — некоректний scroll tracking

[`scroll.ts`](../src/lib/scroll.ts#L15) слухає `window`, тоді як список прокручується у вкладеному `<main>`: [`+layout.svelte`](../src/routes/%28app%29/+layout.svelte#L70).

Через це напрямок прокрутки визначається неправильно, а рух угору може помилково позначати записи прочитаними.

Рекомендація: передавати фактичний scroll container в tracker або визначати напрямок у callback observer через попередню позицію елемента.

### P2 — синхронний повний запис OG cache

Після кожного знайденого зображення весь OG-cache синхронно серіалізується в `localStorage`: [`entries.svelte.ts`](../src/lib/stores/entries.svelte.ts#L595).

Рекомендації: debounce/batching, лімітований LRU або IndexedDB.

### P2 — необмежений fan-out запитів

Іконки всіх feeds та refresh усієї категорії запускаються необмеженим `Promise.all`:

- [`feeds.svelte.ts`, icons](../src/lib/stores/feeds.svelte.ts#L173)
- [`feeds.svelte.ts`, category refresh](../src/lib/stores/feeds.svelte.ts#L497)

Рекомендація: обмежити конкурентність до 4–8 запитів.

## Якість коду та рефакторинг

### P1 — type checking не є частиною build

`svelte-check` знайшов **20 errors і 39 warnings у 12 файлах**. Серед реальних помилок:

- відсутній `@types/node`;
- неправильний тип компонентів іконок у [`ContextMenu.svelte`](../src/lib/components/ui/ContextMenu.svelte#L4);
- nullable `scroller` у `FeedSettings.svelte`;
- необроблені `undefined` route params;
- некоректний lifecycle callback у layout.

У [`package.json`](../package.json#L5) немає `check`, lint або test scripts. Через це production build проходить попри типові помилки.

Рекомендації:

- Додати `svelte-check` та `@types/node` у dev dependencies.
- Додати scripts `check`, `lint`, `test`.
- Зробити їх обов'язковими перед deploy.

### P1 — неправильний lifecycle cleanup

[`+layout.svelte`](../src/routes/%28app%29/+layout.svelte#L30) використовує `onMount(async () => ...)`. Cleanup, повернений після `await`, не реєструється Svelte, тому listener `matchMedia` не знімається.

Рекомендація: залишити callback `onMount` синхронним, запускати внутрішню async-функцію окремо і повертати cleanup безпосередньо.

### P2 — надмірно великі модулі

- `entries.svelte.ts` — 784 рядки.
- `feeds.svelte.ts` — 544 рядки.
- `FeedSettings.svelte` — понад 700 рядків.

Рекомендована декомпозиція:

- API orchestration;
- entry enrichment;
- thumbnails/cache;
- client-side filters;
- mutations і counters;
- UI state та presentation components.

### P2 — imperative `$effect` і stale async responses

Сторінки використовують `$effect` для завантаження даних і мутації state. При швидкій навігації старий async response може оновити вже інший route.

Рекомендація: централізований abortable loader або generation token, derived route params і явні event-driven mutations.

### P2 — конфлікт тимчасових settings-файлів

Settings використовує спільний `${filePath}.tmp`; паралельні PUT одного користувача можуть конфліктувати.

Рекомендація: унікальний temp-файл для кожного запису та серіалізація записів одного користувача.

### P3 — Svelte best practices

Svelte-аналізатор також знайшов:

- неключовані `each` у FeedTree, ContextMenu та BridgeFeedWizard;
- надмірне використання `$effect` для state mutation;
- внутрішні navigation paths без `resolve()`;
- застарілі або зайві `svelte-ignore` comments.

## План виправлень

### Етап 1 — блокуючі ризики

1. Спільний `safeFetch` із SSRF protection.
2. Автентифікація і rate limiting server-side fetch endpoint-ів.
3. Санітизація всього HTML перед `{@html}`.
4. Streaming limits і timeout.
5. `Cache-Control: no-store` та security headers.

### Етап 2 — стабільність

1. Усунути всі `svelte-check` errors.
2. Виправити lifecycle cleanup і scroll tracking.
3. Додати abort/generation guards до async loaders.
4. Виправити конкурентний запис settings.

### Етап 3 — продуктивність і підтримуваність

1. Один DOM parse на entry.
2. Спільний IntersectionObserver.
3. Лімітований і пакетний cache persistence.
4. Bounded concurrency для fan-out запитів.
5. Декомпозиція store та UI-компонентів.
6. Unit та integration tests для proxy security, filters, mark-read і settings sync.
